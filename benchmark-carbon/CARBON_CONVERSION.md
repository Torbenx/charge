# Converting the Charge benchmark corpus to Carbon

Record of how `benchmark/*.chrg` was translated into the
Carbon sources in this directory, and the reference for redoing or extending
that translation.

**Status: done.** All 16 files are converted and parse clean. `convert.py` in
this directory is the converter; it is deterministic and re-runnable.

**Goal:** the converted files parse. They are *not* expected to pass semantic
analysis (neither do the originals — `std.chrg` says so explicitly).

## Layout

| | |
|---|---|
| Source | `benchmark/*.chrg` |
| Output | `benchmark-carbon/*.carbon` (this directory) |
| Converter | `benchmark-carbon/convert.py` |

```sh
# regenerate one file
python3 benchmark-carbon/convert.py benchmark/std.chrg benchmark-carbon/std.carbon

# regenerate everything
for f in benchmark/*.chrg; do
  n=$(basename "$f" .chrg)
  case $n in benchmark*|slab_allocator-tiny) continue;; esac
  python3 benchmark-carbon/convert.py "$f" "benchmark-carbon/$n.carbon"
done
```

**Not converted, deliberately:**

* `benchmark.chrg`, `benchmark-nocomments.chrg`, `benchmark-blockcomments.chrg`
  — generated by `benchmark.py` from the other files; they are produced
  separately once the sources are converted.
* `slab_allocator-tiny.chrg` — a truncation of `slab_allocator.chrg`, not an
  independent source.

**Validation:**

```sh
<carbon-dir>/bazel-bin/toolchain/install/carbon-busybox compile \
    --no-include-carbon-core --phase=parse \
    benchmark-carbon/<file>.carbon
```

Exit status 0 with no diagnostics means success. All 16 converted files pass.

Everything in the mapping tables below was checked against
`carbon-busybox` (built from `trunk` at `db2e26b`) and against Charge's
grammar in `compiler/parse/parse.txt` and `compiler/parse/keyword_table.gperf`.
The decisions taken are recorded in
[§10 Decisions](#10-decisions).

## 2. Line-by-line policy

The conversion is line-for-line everywhere except operator overloads. Three of
the four constructs where Charge and Carbon disagree on line count are kept 1:1
with a formatting split; the fourth cannot be.

| Charge | Carbon | 1:1? |
|---|---|---|
| `template(...)` + `struct X: {` | `class X(...)` + `{` | **Yes** — split the header (§4.4) |
| `template(...)` + `fn f(...)` | `fn f[...]` + `    (...)` | **Yes** — same trick (§4.4) |
| `namespace n: { ... }` | `namespace n;` … blank line | **Yes** — blank out the `}` (§4.1) |
| `enum X: { A; B = 2; }` | `choice X { A, B, }` | **Yes** — 1:1 per line (§4.3) |
| `fn impl (a + b)(...)` | `impl ... { fn Op ... }` | **No** — [D3](#d3-operator-overloads-fn-impl-a--b) |

Measured result — the only files that change length are the three carrying
operator overloads, and the growth is exactly the cost of
[D3](#d3-operator-overloads-fn-impl-a--b):

| File | Charge | Carbon | Δ |
|---|---:|---:|---:|
| `particle_sim` | 6 063 | 6 141 | +78 |
| `bignum` | 1 578 | 1 593 | +15 |
| `chess_movegen` | 4 280 | 4 285 | +5 |
| *the other 13 files* | — | — | **0** |

Within a line, two rewrites change token counts:
[D1](#d1-assert--prove--discard--destroy) adds two tokens per statement across
1 162 statements, and [D2](#d2-designated-call-arguments) adds two per call plus
one per argument across ~904 lines. Together that is well under 1% of the
corpus. If the benchmark is ever recalibrated on token counts rather than
lines, revisit those two.

## 3. Lexical mapping

### 3.1 Comments

Charge and Carbon both use `//`. Two differences:

* **Carbon requires whitespace (or end of line) after `//`.** `//no space` is a
  lex error. The corpus already writes `// text` everywhere, but the separator
  lines `// --- Tuning constants ---` are fine (space follows `//`).
* **Carbon has no block comments.** `/* ... */` does not lex. Only affects the
  generated `benchmark-blockcomments.chrg` variant ([D7](#d7-benchmark-blockcommentschrg-has-no-carbon-equivalent)).

Trailing comments on a code line are fine in both.

### 3.2 Identifier collisions

Charge identifiers that are Carbon keywords must be renamed. Scanning the corpus
with comments and string literals stripped, exactly **seven** names collide:

| Charge identifier | Occurrences | Suggested rename |
|---|---:|---|
| `constraint` | 56 | `constraint_` |
| `base` | 52 (params, locals, one method) | `base_` |
| `class` | 24 (parameter name) | `class_` |
| `where` | 12 (parameter + member) | `where_` |
| `form` | 10 (parameter name) | `form_` |
| `partial` | 8 (local) | `partial_` |
| `alias` | 7 (param, local, in `add_alias`) | `alias_` |

Note `add_alias` as a *function* name is fine — only the bare identifier `alias`
collides. Rename occurrences of the bare token only.

These look like collisions but are **not** — they occur only inside string
literals or comments, so leave them alone: `auto`, `array`, `match`, `not`, `or`,
`and`, `then`, `runtime`, `eval`, `unused`.

These are Charge keywords too and are handled structurally, not by renaming:
`const fn if let return self static var while for break continue else template
namespace impl in`.

`true` and `false` are plain identifiers in Charge (`true_value`, `false_value`
in `std.chrg` are separate names) and become Carbon's boolean keyword literals —
no action needed.

### 3.3 Literals

| Charge | Carbon | Notes |
|---|---|---|
| `16`, `4096`, `1000000000` | unchanged | Corpus has no hex or binary literals. |
| `12.5` | unchanged | Exactly one float in the corpus. |
| `"text"` | unchanged | |
| `'a'` | `'a'` | Carbon does have single-quote character literals. |
| `'\n' '\t' '\r' '\0' '\\' '\"'` | unchanged | Supported by both. |
| `'\f'` (6×) | `'\u{0C}'` | Carbon has no `\f`. |
| `'\b'` (5×) | `'\u{08}'` | Carbon has no `\b`. |
| `'\v'` (1×) | `'\u{0B}'` | Carbon has no `\v`. |

Carbon also rejects `\x41` *inside a character literal* (it suggests `\u{41}`);
`\x41` is fine in a string. The corpus has no `\x` escapes, so this is
informational.

## 4. Declarations

### 4.1 Namespaces

Charge namespaces are **blocks**; Carbon namespaces are **declarations**. Carbon
rejects `namespace Foo { }` outright (`namespace declarations must end with a ;`).

```
// Charge                           // Carbon
namespace containers: {             namespace containers;
    ...                                 ...
}                                   (blank line)
```

The matching `}` becomes a blank line, keeping line numbers aligned. Declarations
inside are *not* re-qualified — Carbon only needs `fn containers.Foo()` for name
lookup, which is a check-phase concern, and unqualified declarations parse
fine. See [D4](#d4-namespace-membership-is-lost).

The corpus uses 24 namespaces, one per file plus a few nested, and never puts
two namespaces in one file except through the generated concatenations.

### 4.2 Structs → classes

```
// Charge                           // Carbon
struct SizeClass: {                 class SizeClass {
    fn stride_of(...) -> int: {         fn stride_of(...) -> int {
        return .stride;                     return self.stride;
    }                                   }
    index: int = 0;                     var index: int = 0;
    kind: ClassKind = ...;              var kind: ClassKind = ...;
}                                   }
```

Two changes: `struct X: {` → `class X {` (drop the colon), and every data member
gains a `var` introducer. Members without initializers (`key: K;`) become
`var key: K;` — Carbon allows a `var` with no initializer.

### 4.3 Enums → choices

```
// Charge                           // Carbon
enum SlotState: {                   choice SlotState {
    Empty;                              Empty,
    Occupied;                           Occupied,
    Tombstone = 2;                      Tombstone,
}                                   }
```

Per line: `X;` → `X,` and `Y = N;` → `Y,`. A trailing comma before `}` is legal
Carbon, so every member gets one and the rule stays uniform. Line count is
preserved.

Two shapes occur. Most enums number only their last member, but
`bytecode_vm.chrg` numbers **every** member and puts a hex comment after each:

```
// Charge                                   // Carbon
Constant = 0;          // 0x00              Constant,          // 0x00
ConstantLong = 1;      // 0x01              ConstantLong,      // 0x01
```

so the rule has to tolerate a trailing comment on the member line. (It did not
at first, and the parser caught it.)

`SlotState::Empty` at use sites becomes `SlotState.Empty` via the general
`::` → `.` rule in §6.2 — nothing special needed.

**The explicit ordinals are lost** ([D5](#d5-enum-ordinals-are-lost)).

### 4.4 Templates → parameterized classes and functions

Charge writes `template(...)` on its own line above a struct. Carbon puts the
parameters on the class header. To keep 1:1 lines, split the Carbon header
across the same two lines:

```
// Charge                           // Carbon
template(K: type, V: type)          class Slot(K: type, V: type)
struct Slot: {                      {
```

Carbon is whitespace-insensitive here; this was verified to parse. Note current
Carbon no longer uses `:!` — `class Slot(K:! type)` is a **parse error**. A
plain `(K: type, V: type)` parameter list is implicitly generic.

For functions the parameters move into square brackets. Charge writes the
template inline in 7 cases, which stays on one line:

```
// Charge
template(T: type) fn min(a: &const T, b: &const T) -> &const[a, b] T: { }
// Carbon
fn min[T: type](a: T, b: T) -> ref const T { }
```

and on a separate line in **128** cases, which splits the same way as a class
header to keep line parity:

```
// Charge                                 // Carbon
template(V: type, W: type)                fn bfs[V: type, W: type]
fn bfs(g: &const shared AdjacencyList{V, W},   (g: AdjacencyList(V, W),
       source: int) -> SearchResult{V}: {       source: int) -> SearchResult(V) {
```

This case is worth care: dropping the `template` line instead still **parses**,
because a function with no generic parameters is perfectly good Carbon. The
parser cannot catch it; only the line-count check did.

Non-type template parameters work the same way: `template(K: type, V: type,
ORDER: int)` → `class BTree(K: type, V: type, ORDER: int)`.

### 4.5 Globals

```
// Charge                           // Carbon
static DEFAULT_CAPACITY: int = 16;  let DEFAULT_CAPACITY: int = 16;
static var counter: int = 0;        var counter: int = 0;
static true_value: bool;            let true_value: bool;
```

878 `static` globals, of which 69 are `static var`. Carbon accepts a file-scope
`let` with no initializer, so the `std.chrg` stubs translate directly.

`static open X` exists in Charge's grammar but is unused in the corpus.

### 4.6 Functions

```
// Charge                                  // Carbon
fn align_up(value: int, alignment: int)    fn align_up(value: int, alignment: int)
    -> int: {                                  -> int {
fn is_aligned(value: int) -> bool: { }     fn is_aligned(value: int) -> bool { }
fn page_of(offset: int) => offset >> PS;   fn page_of(offset: int) => offset >> PS;
```

The colon before the body is dropped; everything else is identical. Charge's
expression-body form `fn f(...) => expr;` is **valid Carbon verbatim** (36
occurrences, all in `slab_allocator.chrg` and `utf8_codec.chrg`).

Multi-line parameter lists (Charge wraps long signatures) need no special
handling — only the line carrying `: {` changes.

### 4.7 The `std.chrg` scalar stubs

`std.chrg` declares `int`, `bits`, `byte`, `bool`, `char` as empty structs.
`bool` and `char` are Carbon keywords, so `class bool { }` is a parse error;
`int`, `bits`, `byte` are ordinary identifiers and convert normally.

Recommended: use Carbon's built-in `bool` and `char` at the 779 + 377 use sites
(no edit needed — they already spell the keyword) and replace the two
declaration lines:

```
// Charge                           // Carbon
struct bool: { }                    // bool is built in
struct char: { }                    // char is built in
```

The alternative — renaming to `class Bool { }` / `class Char { }` — costs
1 156 additional edits and is not more faithful. See
[D6](#d6-scalar-type-names).

## 5. Types and references

Carbon has reference bindings, so Charge's references map onto real Carbon
constructs rather than onto pointers: `self` / `ref self` receivers,
`ref a: T` parameter bindings, and `-> ref T` returns. What does *not* survive
is Charge's `unique` vs `shared` distinction and its borrow lists
([D9](#d9-residual-reference-category-loss)).

The corpus uses a very small set of forms — three `self` spellings and five
parameter spellings — so the mapping is mechanical.

### 5.1 `self` parameters — only three forms exist

| Charge | Count | Carbon |
|---|---:|---|
| `self: &const shared` | 1 050 | `self` |
| `self: &unique` | 837 | `ref self` |
| `self: &shared` | 73 | `ref self` |

```
fn size(self: &const shared) -> int: {     →   fn size(self) -> int {
fn clear(self: &unique): {                 →   fn clear(ref self) {
fn insert(self: &unique, key: K) -> bool:  →   fn insert(ref self, key: K) -> bool {
```

`addr self` was removed from Carbon and is a parse error — do not use it.

### 5.2 Other parameters

Carbon **does** have reference parameters. The documented form is a `ref`
**binding pattern**, i.e. `ref` goes before the name, not before the type:

> `binding-pattern ::= ref? (identifier : expression | self (: expression)?)`
> — `docs/design/pattern_matching.md`

So `ref a: T`, not `a: ref T`. Both spellings happen to *parse*, but they mean
different things and only the first is a parameter reference:

```
fn B(a: ref i32) { }   // parses, but check says:
                       //   error: `ref` tag is not an argument to a `ref` parameter
```

`ref T` is only valid as an *extended return type* (`-> ref T`, §5.3) and as a
`ref`-tagged **argument** at a call site. In a parameter list it is a mistake
that the parse phase does not catch. Use `ref a: T`.

| Charge | Count | Carbon | Rationale |
|---|---:|---|---|
| `key: &const shared K` | 1 296 | `key: K` | Immutable borrow ≈ value binding (see below). |
| `key: &const K` | 384 | `key: K` | Same — Charge's bare `&const` *is* `ConstSharedReference`. |
| `a: &unique T` | 305 | `ref a: T` | Mutable exclusive borrow = reference binding. |
| `a: &shared T` | 18 | `ref a: T` | Mutable shared borrow = reference binding. |
| `a: &unique const T` | 1 | `ref a: const T` | Only one occurrence, in `compression.chrg`. |
| `n: int` (no `&`) | — | `n: int` | Unchanged. |

**Why `&const` maps to a value binding rather than `ref a: const T`.** Carbon
*does* accept `ref a: const T` (verified), but any `ref` parameter — const or
not — forces the **caller** to tag the argument:

```
fn ConstRef(ref a: const i32) -> i32 { return a; }
ConstRef(x);       // error: argument to `ref` parameter not marked with `ref`
ConstRef(ref x);   // ok
```

Using `ref a: const T` for all 1 680 immutable parameters would push a `ref`
tag onto every corresponding argument at thousands of call sites. A value
binding is both cheaper and what a Carbon programmer would actually write for
an immutable parameter — Carbon's value semantics pick the representation.

**Call sites of the 305 mutable ones do still need `ref`.** 168 function
declarations take a non-`self` `&unique`/`&shared` parameter, including
`std.chrg`'s `swap` (20 call sites) and `move` (71 call sites):

```
// Charge                              // Carbon
swap(slot.key, pending.key);           swap(ref slot.key, ref pending.key);
var old = move(.slots);                var old = move(ref self.slots);
```

This is a **check-phase** requirement — the untagged form parses fine. Whether
to do it is [D8](#d8-ref-tags-at-call-sites).

**`ref self` methods are exempt.** Verified: a method declared `fn Bump(ref self)`
is called as `c.Bump()`, with no `ref` at the call site. So the 837 + 73
`self: &unique` / `self: &shared` methods from §5.1 impose no call-site work at
all — only the 305 explicit parameters do.

Where Charge dereferences a parameter that became a value binding (`*key`, from
`&const K`), the `*` still parses as a prefix dereference, so bodies can be left
alone. It will not type-check, which is out of scope.

### 5.3 Return types and borrow lists

66 functions return a borrow with an explicit provenance list. Carbon has no
borrow lists, so the `[...]` is dropped; `ref` survives as a return
*category-tag*, which is the documented Carbon grammar for reference returns
(`extended-return-type ::= category-tag expression`, where
`category-tag ::= val | ref | var`):

```
-> &shared[self] V              →   -> ref V
-> &unique[self] Bitmap         →   -> ref Bitmap
-> &shared[unique self] Block   →   -> ref Block
-> &const[self] SizeClass       →   -> ref const SizeClass
-> &const[a, b] T               →   -> ref const T
-> &const shared[self] Token    →   -> ref const Token
```

`ref const T` as a return type was verified to parse and check. All 2 301 plain
`-> T` returns are unchanged.

### 5.4 Parameterized type spellings

Charge uses braces for type arguments, Carbon uses parentheses (1 693
occurrences):

```
vector{Slot{K, V}}          →   vector(Slot(K, V))
map{string, int}            →   map(string, int)
pair{string, V}             →   pair(string, V)
unique_ptr{T}               →   unique_ptr(T)
BTree{int, string, 16}      →   BTree(int, string, 16)
```

This applies to type positions and to call targets alike:
`Slot{K, V}(...)` → `Slot(K, V)(...)`.

## 6. Expressions

### 6.1 Implicit self

Charge's leading `.` is an implicit `self` reference — 7 998 occurrences.

```
return .count;                      →   return self.count;
return h & (.slots.size() - 1);     →   return h & (self.slots.size() - 1);
.count += 1;                        →   self.count += 1;
Bitboard(bits: .bits | other.bits)  →   Bitboard({.bits = self.bits | other.bits})
```

**Rule:** a `.` **not** preceded by an identifier, `)`, `]`, `}` or a digit is an
implicit self and gains a `self` prefix. There are 13 772 ordinary member-access
dots that must be left alone, so a naive `s/\./self./` will not work — the
preceding character must be checked. Beware the `.field = value` struct-literal
syntax introduced by §6.4: apply the implicit-self pass **before** rewriting
designated arguments, or exclude the `{`-preceded case.

### 6.2 Static access

```
SlotState::Empty            →   SlotState.Empty
TokenKind::Plus             →   TokenKind.Plus
```

All 2 917 occurrences are `Type::Member`; a plain `::` → `.` substitution is
safe.

### 6.3 Operators

| Charge | Carbon | Count |
|---|---|---:|
| `&&` | `and` | 378 |
| `\|\|` | `or` | 271 |
| `!x` | `not x` | 415 |
| `~x` | `^x` | 14 |
| `a ^ b` | `a ^ b` | — (infix xor is unchanged; Carbon distinguishes prefix from infix `^`) |
| `+ - * / % & \| << >> == != < <= > >=` | unchanged | |
| `+= -= *= /= %= &= \|= ^= <<= >>=` | unchanged | |
| `&&=`, `\|\|=` | no Carbon equivalent | unused in corpus |

| `a[i]`, `a(x)`, `a.b` | unchanged | |

### 6.4 Designated call arguments

Charge names call arguments with `name:`; Carbon rejects both `f(name: v)` and
`f(.name = v)`. The closest parsing form is a struct literal argument:

```
// Charge
Bitboard(bits: .bits | other.bits)
Slot{K, V}(key: key, value: value, hash: h)
BreakRange(first: 0, last: 9, property: GraphemeBreak::ControlBreak)

// Carbon
Bitboard({.bits = self.bits | other.bits})
Slot(K, V)({.key = key, .value = value, .hash = h})
BreakRange({.first = 0, .last = 9, .property = GraphemeBreak.ControlBreak})
```

~904 lines are affected. This adds two tokens per call and one per argument —
see [D2](#d2-designated-call-arguments) for the alternative.

### 6.5 Parenthesization — the one non-mechanical rewrite

Charge follows C precedence. **Carbon deliberately leaves many operator pairs
incomparable and requires explicit parentheses**, raising
`parentheses are required to disambiguate operator precedence`.

From `toolchain/parse/precedence.cpp`, Carbon's precedence graph is:

```
                    Highest (calls, member access, literals)
                       │
        ┌──────────────┴──────────────┐
    TermPrefix (*x, &x)          LogicalPrefix (not x)
        │                             │
  NumericPrefix (-x), BitwisePrefix (^x)
        │
  ┌─────┼──────┬────────┬──────┬──────┬────────┐
  As  Multiplicative  Modulo  BitAnd  BitOr  BitXor  BitShift
        │  (* /)        (%)    (&)     (|)    (^)    (<< >>)
     Additive (+ -)
        └──────┴────────┴──────┴──────┴────────┘
                       │
              Relational (== != < <= > >=)
                       │
              LogicalAnd (and), LogicalOr (or)
```

Siblings in that diagram are **incomparable** — mixing them without parentheses
is an error. Consequences for this corpus:

| Pattern | Legal in Charge | Carbon requires |
|---|---|---|
| `a * b % c` | yes | `(a * b) % c` — `*`/`/` and `%` are different levels |
| `a + b << c` | yes | `(a + b) << c` |
| `a & b \| c` | yes | `(a & b) \| c` |
| `a & b ^ c` | yes | `(a & b) ^ c` |
| `a + b & c` | yes | `(a + b) & c` |
| `a && b \|\| c` | yes | `(a and b) or c` |
| `a < b == c` | yes | `(a < b) == c` |
| `a % b % c` | yes | `(a % b) % c` — `%` is non-associative |
| `a << b << c` | yes | `(a << b) << c` — shifts are non-associative |

Still legal without parentheses: `a and b and c`, `a or b or c`, `a & b & c`,
`a + b * c`, `a == b and c == d`, `not a and b`, `-a * b`, `^a & b`,
`(a & b) == 0`, `a * b / c`.

The Charge sources are already heavily parenthesized (`(value + mask) & ~mask`,
`(bytes + PAGE_MASK) >> PAGE_SHIFT`, `(part * PERMILLE) / whole`), so the
residue is small: a scan found ~7 lines mixing `%` with `*`/`/`, ~71 mixing
shifts with `+`/`-`, and 4 mixing `&&` with `||`. **Do not try to predict these
— let the parser find them** (§11).

## 7. Statements

| Charge | Carbon |
|---|---|
| `{ ... }` compound | `{ ... }` |
| `if cond: { ... }` | `if (cond) { ... }` |
| `} else: {` | `} else {` |
| `} else: { if c: {` | `} else { if (c) {` |
| `while cond: { ... }` | `while (cond) { ... }` |
| `loop: { ... }` | `while (true) { ... }` |
| `for x: &const in xs: { ... }` | `for (x in xs) { ... }` |
| `for x: &unique in xs: { ... }` | `for (x in xs) { ... }` |
| `for var x: &const in xs: { ... }` | `for (var x in xs) { ... }` |
| `break;` / `continue;` | unchanged |
| `return e;` / `return;` | unchanged |
| `let x = e;` | `let x = e;` |
| `let x: T = e;` | `let x: T = e;` |
| `let x: &shared = e;` | `let ref x: auto = e;` |
| `var x: int = 0;` | `var x: int = 0;` |
| `var x = e;` | `var x = e;` |
| `x = e;` / `x += e;` | unchanged |
| `expr;` | unchanged |
| `assert e;` | `Assert(e);` — see [D1](#d1-assert--prove--discard--destroy) |
| `prove e;` | `Prove(e);` — see [D1](#d1-assert--prove--discard--destroy) |
| `discard e;` | `Discard(e);` — see [D1](#d1-assert--prove--discard--destroy) |
| `destroy e;` | `Destroy(e);` — see [D1](#d1-assert--prove--discard--destroy) |

Notes:

* Carbon requires parentheses around `if`/`while` conditions and around the whole
  `for` clause. Charge does not use them.
* Every `if`/`while`/`for`/`loop` body in the corpus is already braced (checked:
  0 brace-less bodies), and Carbon requires braces — nothing to do.
* There is no `else if` chain in the corpus; Charge writes `} else: { if ... }`.
  Carbon supports `else if (c) {` directly, but the nested form translates 1:1
  and needs no restructuring.
* `loop:` has no direct Carbon equivalent; `while (true)` is the idiomatic
  substitute. 34 occurrences.
* Charge's `do: { } while c;` is in the grammar but **unused** — no mapping
  needed.
* Carbon's `observe` is **not** a substitute for `prove`: it only accepts `==`
  and `impls` operands (`observe a > 0;` is an error).
* `_ = e;` is **not** valid Carbon and cannot be used for `discard`.

## 8. Operator overloads (`fn impl`)

80 declarations, all of the form `fn impl (<op>)(<lhs>, <rhs>) -> T:`, spread
over `bignum`, `chess_movegen` and `particle_sim`:

| Charge operator form | Count | Carbon interface |
|---|---:|---|
| `(a == b)` | 11 | `Core.EqWith(Other)`, `fn Equal(self, other) -> bool` |
| `(a != b)` | 6 | `Core.EqWith(Other)`, `fn NotEqual(...)` |
| `(a < b)` / `(a <= b)` / `(a > b)` / `(a >= b)` | 8/3/6/3 | `Core.OrderedWith(Other)`, `fn Less` / `LessOrEquivalent` / `Greater` / `GreaterOrEquivalent` |
| `(a + b)` | 7 | `Core.AddWith(Other) where .Result = R`, `fn Op` |
| `(a - b)` | 5 | `Core.SubWith(Other) where .Result = R` |
| `(a * b)` | 12 | `Core.MulWith(Other) where .Result = R` |
| `(a / b)` | 6 | `Core.DivWith(Other) where .Result = R` |
| `(a % b)` | 3 | `Core.ModWith(Other) where .Result = R` |
| `(a & b)` / `(a \| b)` / `(a ^ b)` | 1/1/1 | `Core.BitAndWith` / `BitOrWith` / `BitXorWith` |
| `(-a)` | 4 | `Core.Negate where .Result = R`, `fn Op(self)` |

Faithful translation (verified to parse):

```
// Charge — one line
fn impl (a + b)(l: &const shared Vec2, r: &const shared Vec2) -> Vec2: {
    return vec2(l.x + r.x, l.y + r.y);
}

// Carbon — three extra lines, and the body must be rewritten
impl Vec2 as Core.AddWith(Vec2) where .Result = Vec2 {
  fn Op(self, other: Vec2) -> Vec2 {
    return vec2(self.x + other.x, self.y + other.y);
  }
}
```

This is the only construct that does not stay line-for-line, and it also forces
renaming `l`/`r` (or `left`/`right`) to `self`/`other` throughout each body.
Consecutive declarations targeting the same impl are merged into one block, so
`==`/`!=` and the four relational operators each produce a single `impl`; see
[D3](#d3-operator-overloads-fn-impl-a--b) for the merge and its residue.

## 10. Decisions

Every question the mapping raised, and what was actually done. Except for D3,
these follow the recommendation that was on the table; **D3 was decided the
other way** — in favour of faithful Carbon over cheap conversion.

### D1. `assert` / `prove` / `discard` / `destroy`

1 162 statements (383 + 125 + 334 + 320) use Charge keyword statements Carbon
has no form for.

**Decision: rewrite as calls.** `assert e;` → `Assert(e);`, and likewise
`Prove`, `Discard`, `Destroy`. Every line is preserved and the result reads as
plausible Carbon; the cost is ~2 300 extra tokens on a ~50 000-line corpus,
under 1%.

Rejected: bare expression statements (`destroy old;` → `old;` reads badly) and
deleting the statements (removes 1 162 lines of real code).

### D2. Designated call arguments

~904 lines, ~2 400 named arguments. Carbon rejects both `f(name: v)` and
`f(.name = v)`.

**Decision: struct-literal argument.** `Bitboard(bits: e)` →
`Bitboard({.bits = e})`. Keeps the names, which carry much of the corpus's
readability, and is what a Carbon programmer would write.

Rejected: dropping the names.

### D3. Operator overloads (`fn impl (a + b)`)

80 declarations in `bignum`, `chess_movegen` and `particle_sim`.

**Decision: full `impl ... as Core.XWith` expansion** — the faithful Carbon
form, not the cheap flattening to plain named functions. This is the one place
the conversion is not line-for-line.

```
// Charge — one line
fn impl (a + b)(l: &const shared Vec2, r: &const shared Vec2) -> Vec2: {
    return vec2(l.x + r.x, l.y + r.y);
}

// Carbon
impl Vec2 as Core.AddWith(Vec2) where .Result = Vec2 {
  fn Op(self, other: Vec2) -> Vec2 {
      return vec2(self.x + other.x, self.y + other.y);
  }
}
```

The converter also **merges** consecutive declarations that target the same
impl, so `==`/`!=` become one `EqWith` block and `<`/`<=`/`>`/`>=` become one
`OrderedWith` block rather than two and four conflicting impls:

```
impl Vec2 as Core.OrderedWith(Vec2) {
  fn Less(self, other: Vec2) -> bool { ... }
  fn LessOrEquivalent(self, other: Vec2) -> bool { ... }
  fn Greater(self, other: Vec2) -> bool { ... }
  fn GreaterOrEquivalent(self, other: Vec2) -> bool { ... }
}
```

This works because Charge groups them adjacently in all three files. Each body
also has its `l`/`r` (or `left`/`right`) parameters renamed to `self`/`other`.

Total cost: **+98 lines**, all in the three files listed in §2.

Known residue, all check-phase only: a few types implement `OrderedWith`
partially (`Mat2` defines only `<` and `>`), and the asymmetric arithmetic impls
(`Fixed * Vec2` alongside `Vec2 * Fixed`) are separate impls as Charge wrote
them.

### D4. Namespace membership is lost

`namespace containers;` followed by unqualified declarations parses, but those
declarations land in the file's package scope rather than in `containers`.
Making them real members means qualifying 214 class and 3 013 function
declarations, and Carbon cannot qualify a nested class member at all.

**Decision: accept the loss.** It is a check-phase concept, and the corpus is
explicitly not expected to pass semantic analysis.

### D5. Enum ordinals are lost

`Tombstone = 2;` → `Tombstone,`. Carbon `choice` alternatives carry no values.

**Decision: use `choice` and drop the ordinals.** Nothing in the corpus reads
the numbers. Preserving them would mean turning each `choice` into a `class` of
`let` constants, which changes what `x: SlotState` means.

### D6. Scalar type names

`bool` and `char` are Carbon keywords, so `std.chrg`'s `struct bool: { }` and
`struct char: { }` cannot be translated literally.

**Decision: use the built-in `bool` and `char`.** Two declaration lines become
comments; the 1 156 use sites are unchanged because they already spell the
keyword.

```
// Charge                           // Carbon
struct bool: { }                    // bool is built in
struct char: { }                    // char is built in
```

This leaves the corpus slightly uneven — `int`, `bits` and `byte` stay
user-defined classes while `bool` and `char` are built in. Renaming to
`Bool`/`Char` instead would have cost 1 158 edits for no gain.

### D7. `benchmark-blockcomments.chrg` has no Carbon equivalent

That variant exists to measure block-comment lexing. **Carbon has no block
comments** — `/* ... */` does not lex.

Out of scope here: the `benchmark*` files are generated separately. When they
are regenerated, this variant has no faithful counterpart. The nearest
substitute is a triple-quote-delimited block string literal, which Carbon does
have, but it measures something different. **Still open for whoever ports
`benchmark.py`.**

### D8. `ref` tags at call sites

Carbon requires the caller to tag arguments bound to a `ref` parameter:
`swap(ref a, ref b)`. 168 declarations take a non-`self` `&unique`/`&shared`
parameter; `swap` and `move` alone account for 91 call sites.

**Decision: leave call sites untagged.** This is a check-phase rule — untagged
calls parse fine — and matching it would need a cross-file analysis of which
parameters are `ref`, the most expensive pass in the conversion, for a corpus
that was never going to clear `--phase=check`.

`ref self` methods are exempt anyway: `c.Bump()` needs no tag. So this concerns
only the 305 explicit parameters, not the 910 `self` receivers.

### D9. Residual reference-category loss

Charge distinguishes `unique` from `shared`; Carbon's `ref` does not, so
exclusivity information is lost, and the borrow lists (`&shared[self]`,
`&const[a, b]`) are dropped entirely.

**Decision: accept it.** Recorded so nobody is surprised that the converted
corpus cannot be advanced past `--phase=parse`.

### D10. Identifier naming convention

Carbon's convention is `UpperCamelCase` for types and functions; the corpus is
uniformly snake_case.

**Decision: keep Charge's names.** For a parser benchmark, preserving the
identifier-length and identifier-frequency distribution matters more than
matching Carbon style, and the parser does not care. Only the seven
keyword-colliding identifiers in §3.2 were renamed.

## 11. How `convert.py` works

The converter protects string literals, character literals and comments behind
a mask, so every pass below sees only code. Passes run in this order, and the
order matters:

| # | Pass | Section |
|---|---|---|
| 1 | `operator_impls` — expand and merge `fn impl (op)` blocks | §8, [D3](#d3-operator-overloads-fn-impl-a--b) |
| 2 | `rename_clashes` — the 7 keyword-colliding identifiers | §3.2 |
| 3 | `static_access` — `::` → `.` | §6.2 |
| 4 | `implicit_self` — leading `.` → `self.` | §6.1 |
| 5 | `type_args` — `Ident{...}` → `Ident(...)` | §5.4 |
| 6 | `designated_args` — named arguments → struct literals | §6.4 |
| 7 | `statements` — `if`/`while`/`for`/`loop`/`else`, `Assert`/`Prove`/`Discard`/`Destroy` | §7 |
| 8 | `references` — `self` receivers, `ref` bindings, `ref`/`ref const` returns | §5.1–5.3 |
| 9 | `declarations` — namespace, class, choice, template, static, members, `fn` bodies | §4 |
| 10 | `operators` — `&&`→`and`, `\|\|`→`or`, `!`→`not`, `~`→`^` | §6.3 |
| 11 | `parenthesize` — Carbon-required parentheses | §6.5 |
| 12 | `escapes` — `\f` `\b` `\v` → `\u{..}` | §3.3 |

Ordering constraints that are not obvious:

* **`statements` before `references`.** A `for` head reads
  `for entry: &const in old:`; if the reference pass ran first it would try to
  read `in` as the type.
* **`loop:` → `while (true)` last within `statements`.** Done earlier, the
  synthesized `while` gets re-processed by the `while` handler, which then scans
  for a `:` terminator that is not there and runs off the end of the file.
* **`implicit_self` before `designated_args`.** Otherwise the `.field =` that
  the struct-literal rewrite introduces looks like an implicit self.
* **`operator_impls` first**, on raw Charge text, so the bodies it emits flow
  through every later pass. The `where` and `.Result` it writes are held as
  placeholders until the end, or passes 2 and 4 would turn them into `where_`
  and `self.Result`.

### The parenthesization pass

Pass 11 is the only one that has to understand precedence. It folds each binary
operator chain into a tree using **C** precedence (preserving Charge's meaning),
asks whether Carbon would accept that tree unparenthesized, and re-renders with
explicit parentheses only when it would not. Chains that already parse are left
byte-for-byte alone.

Four chains in the corpus needed it, all `%` mixed with another level:

```
i * 37 % 64                          ->  (i * 37) % 64
fraction / divisor % 10              ->  (fraction / divisor) % 10
i * 7 % 32                           ->  (i * 7) % 32
HANGUL_T_FIRST + index % HANGUL_T_COUNT  ->  HANGUL_T_FIRST + (index % HANGUL_T_COUNT)
```

Note the last one parenthesizes the **right** side: `%` binds tighter than `+`
in C, so wrapping the left would silently change the meaning.

### What the parse phase will not catch

Three mistakes produce valid Carbon that means the wrong thing. Two were made
and caught by other means; watch for them when extending the converter.

1. **A dropped `template` line.** A function with no generic parameters parses
   fine. Caught only by comparing line counts (§2) — 128 functions were
   affected.
2. **`a: ref T` in a parameter list.** Parses; means a `ref`-tagged argument,
   not a reference parameter. Caught by `--phase=check` (§5.2).
3. **Untagged arguments to `ref` parameters.** Parses; deliberate
   ([D8](#d8-ref-tags-at-call-sites)).

So the verification loop is: parse every file, compare line counts against the
sources, and spot-check with `--phase=check` — even though the corpus is never
expected to clear that phase.
